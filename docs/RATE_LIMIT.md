# 为什么会被限流（RGV587 被挤爆）

## 现象（2026-10-23 实测）

| 指标 | 数值 |
| --- | --- |
| 当天 Token 刷新次数 | **177 次** |
| 峰值刷新频率 | **9 次/分钟**（14:48–15:00） |
| WebSocket 重连 / 断开 | 162 次 / 167 次 |
| 断开原因 | 全部是 `no close frame received or sent` |
| 平台返回 | `RGV587_ERROR::SM::哎哟喂,被挤爆啦,请稍后重试` |

日志里能看到一个 7 秒一轮的循环：

```
14:44:43 WebSocket 连接建立成功
14:44:43 开始刷新 token → SUCCESS
14:44:45 连接就绪
14:44:47 WebSocket 连接已退出（no close frame）
14:44:47 清空当前 token，重新连接时将重新获取
14:44:50 重新连接 → 又刷新 token
... 循环 16 分钟
```

## 根因

1. **服务端主动断开**：连接建立后约 2~7 秒被断开，且没有 close frame。最常见的原因是
   **同一个账号在别的客户端也登录着**（网页版 `goofish.com/im`、手机 App、另一个服务进程），
   几端互相踢下线。
2. **每次重连都清空 token**：旧代码在重连分支里执行 `self.current_token = None`，
   `init()` 于是每次重连都必须重新请求 token 接口。
3. **重连间隔固定 3 秒**：`connection_failures` 在连接成功时被清零，退避逻辑永远从 3 秒开始，
   于是形成"连上 → 被踢 → 3 秒后重连 → 刷 token"的稳定循环。
4. 结果：token 接口被刷到 mtop 限流（RGV587），随后滑块验证也在高风险状态下必然失败。

## 已修

- 重连时**不再清空 token**，`init()` 按 `token_refresh_interval` 复用；
- `refresh_token` 增加兜底：60 秒内成功刷新过就直接复用，不再发请求；
- 连续快速断开（连接存活 < 10 秒）指数退避：3 → 6 → 12 → 24 → 48 → 96 → 120 秒封顶；
- 连续第 3 次快速断开时打印明确提示：
  「账号可能同时登录了网页版/手机 App（会互相踢下线），请关闭其他客户端」；
- 识别到 `RGV587` / `被挤爆` 时冷却 15 分钟，不再拉起滑块。

## 建议

1. 同一账号只保留一个客户端在线：网页版、手机 App、其他工具用完就退出；
2. 不要同时跑多个服务进程（会互相踢），确认 `ps aux | grep Start.py` 只有一个；
3. 日志出现「连续 N 次快速断开」时，先检查其他客户端，不要急着调滑块参数；
4. 被限流后至少休息 15~30 分钟，期间不要反复触发 token 刷新或滑块。
